## Intent

**Problem:** The project has a subscription architecture but no implemented entitlement issuer or target verifier, so a payment-confirmed customer cannot receive a defensible remote extension. Directly editing a target database or dropping an unsigned expiry file would bypass the existing security contract.

**Approach:** Add a separate Ed25519 entitlement toolchain. The operator issues a canonical, site-bound grant for Asia/Shanghai `2026-09-04T00:00:00+08:00` through `2027-09-04T00:00:00+08:00`, transfers it over the existing key-only SSH/Tailscale path, and the target verifies and atomically installs it while recording an append-only audit event.

## Boundaries & Constraints

**Always:** Keep the entitlement private key separate from release and payment keys; sign the canonical payload; bind the grant to a stable site identity; include customer, plan, features, issued/start/expiry/grace timestamps, serial, grant id and key id; reject invalid signatures, unknown keys, wrong site, expired/future-invalid, duplicate or replayed grants; preserve the current grant on failed installation; use UTC timestamps with the requested Asia/Shanghai boundary; use the existing protected target directories and SSH authentication; audit operator, target, grant identity, hashes, result and reason without secrets.

**Ask First:** The customer/site identifier, customer display identifier, plan name/features, grace duration, and entitlement signing key custody/rotation owner must be confirmed before production issuance. For this first grant, default grace is 7 days and the target's observed site identity is `deploy-20260903.2` only if no stable site identity is available.

**Never:** Implement automatic renewal, payment-provider calls, automatic deductions, payment credentials on the target, unsigned entitlement files, release-key reuse, database-only expiry edits, disabling monitoring/alarms/stored data/safety functions at expiry, or changing serial mappings, Modbus traffic, device point maps, or business data.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|---------------|-----------------------------|----------------|
| HAPPY_PATH | Approved payment; valid site-bound grant for 2026-09-04..2027-09-04 | Target atomically installs grant and reports `active` with exact boundaries | Audit success; old grant retained until commit |
| BAD_SIGNATURE | Grant bytes or signature changed | Reject before state mutation | Non-secret error and audit `signature_invalid` |
| WRONG_SITE | Valid signature for another site | Reject before state mutation | Audit `site_mismatch` |
| REPLAY_OR_ROLLBACK | Same grant id, lower serial, or older expiry than current | Reject idempotently | Audit `replay_rejected`; current grant remains |
| EXPIRED_OFFLINE | Clock after expiry/grace or central link unavailable | Report `expired`/`grace` only for entitlement-dependent features | Monitoring, alarms, stored data and safety remain available |

**Acceptance Criteria:**
- Given an approved one-year payment confirmation and the confirmed site identity, when the issuer creates a grant, then its canonical payload verifies with the entitlement public key and contains exactly the requested start/end instants.
- Given a valid grant, when the remote installer runs with the same operation identity, then the target returns `installed` or the recorded idempotent result and its status shows the exact site, serial, start, expiry and grace values.
- Given any altered, wrong-site, stale, duplicate or future-invalid grant, when verification runs, then it fails closed before replacing the current state and writes no secret material.
- Given an expired or offline entitlement, when target status is evaluated, then only entitlement-dependent support/upgrade capability changes; collection, alarms, data access and safety behavior continue.
- Given the repository test, lint and PowerShell syntax suites, when they run, then all pass and the unrelated untracked file `D:/江苏润盛/3` is untouched.
- Given a target already provisioned for site A, when an operator supplies site B and a correctly signed site-B grant, then the target rejects it against its locally pinned site identity before state replacement.
- Given a runtime replacement is interrupted after any backup or install move, when the installer is invoked again, then it deterministically completes or rolls back from a protected durable journal and never reports a known partial state as rejected.
- Given an approved grant source is replaced after local inspection, when upload begins, then only the protected snapshot matching the approved canonical digest can be transferred.
- Given a previously accepted runtime epoch or observed entitlement time, when an older signed bundle or a materially earlier clock is presented, then the target rejects the downgrade or reports time uncertainty without restoring expired capability.
- Given protected time was previously observed or an entitlement/runtime transaction is interrupted, when Status waits for a lock or returns `uncertain`, then the committed observation never decreases and the transaction remains recoverable without overwriting an unrecognized third state.
- Given an active or grace grant containing one approved feature, when the corresponding remote operation reaches its target mutation boundary, then only that feature is authorized; expired, missing, uncertain and feature-absent states fail before mutation, while Status, application Start and recovery of an already-started transaction remain usable.
- Given the same approved runtime operation is replayed after a lost Prepare/install/cleanup response, when protected incoming state matches, then it resumes or returns the correlated terminal receipt without double deletion; mismatched state fails closed and retains recovery evidence.
- Given identical vendor and bundle file sets, when manifests are generated or checked under Windows PowerShell 5.1 and PowerShell 7, then both use ordinal ordering and accept exactly the same canonical bytes.
- Given local OpenSSH configuration contains redirect or command-execution directives, when an entitlement transport runs, then `-F NUL` prevents those directives from changing the validated Tailscale destination or process behavior.
- Given concurrent or abandoned grant/runtime uploads, when Prepare reserves target capacity or Cleanup overlaps installation, then aggregate reserved bytes never exceed 128 MiB, only safe stale reservations are reclaimed, and Cleanup cannot delete a bundle held by the installer.

## Design Notes

The first grant should use a new key id and a serial greater than any existing target grant. Grant JSON is accepted only in one canonical UTF-8/LF representation; the trusted OpenSSH public-key comment is the pinned key id. A process-safe transaction lock covers operation replay lookup, old-state comparison, audit preparation, state replacement and recovery metadata so an interrupted install is detected and deterministically recovered before another mutation. Exact fixed paths and ACLs are part of verification, and a Status command must not create directories or alter ACLs. Remote success is accepted only when the returned site, operation, grant identity and canonical digest match the local request. The prior grant remains authoritative until the target commit completes; no entitlement command restarts Windows or Docker.

Confirmed production parameters are stable `site_id=site-win-oaucm8uqugh`, `customer_id=customer-win-oaucm8uqugh`, plan `annual-support-updates`, features `remote-support`, `software-updates`, and `security-patches`, with a 7-day grace period. The separate entitlement private key is owned by the local administrator account and its random passphrase is stored only as current-user DPAPI ciphertext. The active release candidate is not used as the site identity.

Runtime bundles carry a signed positive integer epoch and entitlement-key generation in the authenticated closed manifest. This release requires generation 1 and records the installed public-key digest in protected runtime state; every later runtime must keep both unchanged. In-place entitlement-key rotation is rejected until a separate approved protocol can jointly authenticate and migrate the current grant without an entitlement gap. The target records the highest committed epoch outside the replaceable runtime tree and rejects equal or lower epochs except an exact replay whose site identity, component hashes and vendor closed set all still match.

Runtime and grant mutations share the entitlement byte-range transaction lock. The protected durable runtime journal is written before the operation-specific transaction root is created, covers staging, backups, installed components and final validation, and recovery runs before accepting another bundle. The target's site identity is provisioned only when no committed runtime state exists; after that, a missing or changed identity is failure, and every command treats remote `SiteId` only as an assertion. Local remote tools resolve system OpenSSH and the authenticated local Python 3.11 runtime by absolute path, snapshot approved artifacts before inspection/upload, and use exact cleanup paths. Protected time state never decreases and is observed even for missing grant state; any protected-time corruption or material backward jump produces `uncertain`. State, audit and archive limits are enforced during reads, while bounded operation pruning may remove an old executing receipt only when no active journal references it. These controls must not block Status from reporting an active transaction as uncertain or block deterministic recovery.

Feature authorization is decided on the target from the protected current grant, not from caller-supplied metadata. `active` and `grace` may authorize only features present in the signed closed list. `remote-support` gates debug access and maintenance Stop/Restart, `security-patches` gates a new hotfix deployment, and `software-updates` gates new full-release initialization/apply. Read-only entitlement Status, application Start, runtime/grant repair, and recovery of a deployment whose journal already proves it started are never denied by commercial state. Remote consumers must call the fixed protected verifier at their target execution boundary; a local preflight alone is not authorization.

Canonical filename ordering is ordinal, byte-for-byte consistent across Windows PowerShell 5.1, PowerShell 7 and Python; culture-sensitive `Sort-Object` is not part of the signed format. Every OpenSSH client call ignores ambient user/system configuration with `-F NUL` and supplies all required options explicitly. Runtime state retains exact signed component/vendor identities needed for routine pin checks, while a separate runtime-use gate prevents replacement after those checks and before Python completes. Recovery changes or deletes only states proven equal to journaled old/new identities, and cleanup evidence is retained until removal is verified. Operation replay is guaranteed only within the protected retained terminal-receipt window; expired operation IDs are not represented as indefinitely replayable in operator documentation.

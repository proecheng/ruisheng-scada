# Plan 5 客户机部署与串口真机验收

## Why

Plan 4 已证明系统能在开发机通过 Compose 冒烟和自动化回归，但客户、运维和现场设备尚未获得可复核的部署证据。当前离线部署包还未同步最新告警运行配置，全新安装会写入 Demo 租户、设备和文档公开的固定账号密码，制品也未形成不可变清单；在真实客户环境开放前，必须先消除这些发布阻断项，并用目标等价环境和真实 RS485 设备证明数据、告警与恢复链路。

## Capabilities

- id: CAP-1
  intent: 发布人员可以生成身份固定、可校验且无需联网构建的候选部署包。
  success: 在断网的空白目标机上，使用预先经可信介质安装的包外发布信任锚和候选包即可验证发布者身份并加载全部镜像；Compose 不拉取、不构建，清单中的源提交、目标架构、镜像 ID/摘要和每个归档的 SHA-256 均与实际制品一致，运行身份不依赖可漂移标签。

- id: CAP-2
  intent: 运维人员可以用现场唯一密钥在空白数据卷上完成安全的首次安装。
  success: 迁移任务可安全重试并成功退出，PostgreSQL、Redis、API、GW 和 Web 均就绪；首次对外监听时公开默认密码即不可登录，生产数据中不存在未获批准的 Demo 租户、用户、设备或点位，站点密钥和引导凭据不进入日志、镜像或验收证据。

- id: CAP-3
  intent: 运维人员可以升级现有安装，并在失败时恢复服务和数据。
  success: 从站点实际版本升级或失败重试后，租户、设备、历史、告警和配置保持一致；备份可在空白隔离环境恢复数据库角色、扩展、schema 和数据，并与受控保存的站点配置共同在批准的 RTO/RPO 内恢复服务。

- id: CAP-4
  intent: 运维人员可以按批准的网络边界运行、监控和维护系统。
  success: 从每个相关网段实测只有批准的用户、设备和管理入口可达，认证或控制流量不经不受信网络明文传输；API/GW 探针与指标仅供批准的监控路径使用，主机时钟、磁盘和日志策略符合站点门槛，重启后数据卷和 GW WAL 保持。

- id: CAP-5
  intent: 现场人员可以把至少一台批准的真实 RS485 设备稳定接入 GW，并完成安全的采集与控制闭环。
  success: 系统能表达并应用设备实际串口参数，在 `site-acceptance-profile.md` 批准的持续时间内，点位值、历史和浏览器实时显示一致；断开、重连和 GW 重启后自动恢复，已批准的控制命令有可追溯结果且不产生重复执行。

- id: CAP-6
  intent: 验收人员可以用真实设备越限验证告警从 GW 到 API、Web 和通知审计的完整链路。
  success: 一次首次越限只形成一个告警身份和一套逻辑投递，页面与审计状态一致，恢复后可再次触发；通知供应商保持关闭时不产生外发，只有获得单独授权后才对批准的测试收件人执行真实渠道测试。

- id: CAP-7
  intent: 项目负责人可以按已确认的现场负载验证性能、断网恢复和容量余量。
  success: 在已批准的设备数、点位数、轮询周期、并发和资源模型下，所有门槛均有原始测量证据；批准时长的网络或依赖中断后，恢复时间、数据缺口、重复、告警语义和积压均符合站点策略，任何“零 P0 告警遗漏”声明都有包含告警重放路径的证据。

- id: CAP-8
  intent: 迁移负责人可以在替换遗留系统时依据双跑数据作出切换或回滚决定。
  success: 若本次包含旧系统迁移，则静态配置/历史数据迁移范围有逐项对账，双跑使用互不干扰且可区分来源的路径；在批准周期内每日对账，差异超过批准阈值、出现严重数据丢失或漏发任一 P0 告警时停止切流并回滚。

- id: CAP-9
  intent: 项目负责人可以依据脱敏、可重放的验收证据作出 Go/No-Go 决策。
  success: `site-acceptance-profile.md` 已在测试前批准，`acceptance-matrix.md` 中所有适用项均有环境、执行人、时间、步骤、原始结果和 PASS 结论；N/A 在执行前由对应负责人批准，FAIL/BLOCKED、P0/P1 缺陷和未批准的范围变化均为零。

## Constraints

- 必须同时遵守告警运行规格和全项目质量加固规格；租户隔离、幂等、数据库保护、审计脱敏和 provider 默认关闭不可放宽。
- `site-acceptance-profile.md` 是开测门槛；适用范围、性能阈值、故障时长、RTO/RPO、控制边界或签署人发生变化时，受影响结果失效并须重测。
- 离线部署包必须与根生产配置保持功能等价；当前缺失的通知 worker/provider 变量和 GW 告警刷新变量必须在发布候选前同步并建立回归保护。
- 生产迁移不得无条件运行开发 Demo seeds；首次对外监听前不得存在公开固定凭据或未批准 Demo 数据。
- 真实客户环境、真实设备控制、第三方凭据、真实通知、数据删除、生产迁移或公开 API 变化均须单独获得明确授权。
- 破坏性演练只能针对显式标识的验收实例；生产或客户数据迁移前必须先完成可恢复备份，未经评审不得用数据库 downgrade 代替恢复方案。
- 不得把模拟器、历史抓包或 mock provider 的结果标记为真机、现场容量或真实渠道验收结果。
- 发布候选必须使用不可变版本或摘要；不得以可漂移的 `latest` 作为验收证据中的唯一身份。
- 签名的候选基础文件不得在现场直接编辑；站点差异必须位于独立、受控且可校验的配置或 Compose override 中。
- CRC、截断、乱序等故障注入只能在隔离台架或批准的仿真链路进行，不得向生产总线或未授权真机发送畸形帧。
- 现场控制仅限客户书面批准的设备、点位、值域和时间窗，并预先约定人工急停与回退步骤。
- 未解决目标环境、网络/TLS、串口参数、容量基线、切换窗口和合规要求前，只能完成隔离部署演练，不能宣布 Plan 5 完成。

## Non-goals

- 本规格不授权生产上线、客户数据迁移、真实通知供应商启用或真实支付交易。
- 本规格不实现微信支付正式下单、复位通知、前端覆盖率门禁或 ECharts 包体优化。
- 本规格不以一次冒烟替代持续运行、恢复、容量或遗留系统对账。
- 本规格不替客户决定网络拓扑、合规等级、数据保留期或可接受停机窗口。

## Success signal

在批准的目标环境中，一套以不可变身份标识的离线候选包可从空白状态安全启动，经真实 RS485 设备持续运行、故障恢复、告警闭环和空白环境数据恢复验证后，所有适用 Gate 均为 PASS 并由项目负责人、运维和客户代表签署；不存在公开默认凭据、未批准 Demo 数据、配置漂移或未处置的 P0/P1 阻断项。

## Assumptions

- 首轮执行以隔离、目标等价的 Docker Compose 环境开始，现场和生产操作在开放问题确认后另行授权。
- 客户机部署仍采用当前仓库的 Docker Compose 路径；旧的“Windows 原生服务部署”说明不作为本轮实施依据。
- 真机稳定性首轮建议至少连续运行 24 小时；最终时长由站点负责人在开测前批准。

## Open Questions

- 谁批准 `site-acceptance-profile.md`，目标机器、CPU 架构、操作系统、资源、Docker/WSL2 版本和出入站网络策略分别是什么？
- Web 是否仅限隔离可信网，还是必须提供 HTTPS/WSS、域名、证书和反向代理；health/metrics 由哪个监控网段访问？
- 真机型号、数量、USB/串口映射、波特率、校验位、数据位、停止位、Modbus 地址、点表、允许控制值域和稳定运行时长是什么？
- 现网设备数、点位数、轮询周期、用户并发、日报文量、历史量、磁盘增长和告警量是多少；采用哪些性能与积压门槛？
- 批准的 RTO/RPO、可接受数据缺口/重复策略和依赖中断时长是什么；是否要求中断期间 P0 告警零遗漏？
- 是否替换遗留系统；需迁移哪些用户、组织、设备、点表、告警配置和历史数据，能否提供真机、24 小时抓包、影子路径及双跑条件？
- 是否要求等保、第三方渗透测试或特定日志/审计保留期？
- 本轮是否包含任何真实通知渠道；若包含，供应商、测试账号、批准收件人、配额和测试时间窗分别是什么？

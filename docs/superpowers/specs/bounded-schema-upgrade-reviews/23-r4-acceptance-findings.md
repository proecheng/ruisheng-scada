## A1 — P1: Dynamic PowerShell script-block execution is classified as safe

- Location: `tools/remote_full_upgrade/target-updater.ps1:1928-1932`, with the successful fall-through at line 2039.
- Trigger: a scheduled action executes `powershell.exe` with `-Command "[scriptblock]::Create('docker start ruisheng-gw').Invoke()"`. The inner string can instead contain an old Compose startup command or another business-writing command.
- Evidence: the invocation-expression scan considers only static calls on `Diagnostics.Process`; it silently skips both `ScriptBlock.Create(...)` and the subsequent instance `.Invoke()`. The string containing the command has no nested `CommandAst`, so the following command scan finds nothing to reject and returns `$false`. The actual classifier returned `$false` for this input on PowerShell 7.6.4 and Windows PowerShell 5.1.26100.9168. Direct `docker start ruisheng-gw` returned `$true` on both, and `Write-Output 'docker start ruisheng-gw'` correctly returned `$false`.
- Consequence: `Assert-InstalledMaintenanceGuards` accepts this unprotected task (lines 1653-1657); Apply can pass its initial guard check (3286), and Recover can pass the guard immediately preceding role restoration/start (2775-2779). Thus an actual business-start wrapper can remain capable of starting containers without consulting the persistent maintenance marker, despite the verifier reporting protected startup entry points.
- Violated acceptance: the spec requires rejecting new bypass tasks before unsealing/completing maintenance; context R3 requires refusing wrappers whose business-start behavior cannot be proved safe, and R4 explicitly says dynamic indirect execution must not fall into the default-safe case. A bounded treatment of recognized script-block construction/invocation, or refusal where that behavior cannot be proved, is required without turning harmless quoted output into a rejection.

## A2 — P1: Extensionless relative PowerShell scripts bypass script identity checks

- Location: `tools/remote_full_upgrade/target-updater.ps1:1789-1791` and `2031-2042` (especially the unconditional final `$false` at 2042).
- Trigger: a scheduled PowerShell command invokes `& .\wrapper` in a working directory containing `wrapper.ps1` that starts business containers. PowerShell can resolve the script with its `.ps1` extension omitted.
- Evidence: the real classifier returned `$false` for `-Command '& .\wrapper'` on both PowerShell editions above. The `CommandAst` supplies the literal name `.\wrapper`; recursion checks only its literal extension, misses the `.ps1/.cmd/.bat` branch, and ends in the generic safe result. No path, digest, ACL, content, or missing-file proof is requested. In contrast, the CMD branch explicitly handles extensionless lookup at lines 1873-1877, demonstrating that the protection is absent specifically from the PowerShell command path. The added R4 test matrix covers extensionless CMD scripts, but not this PowerShell counterpart.
- Consequence: unknown relative scripts can evade both the initial installed-entry gate and Recover's recheck. The filename need not be an approved helper, and its contents can be changed to bypass maintenance without the verifier examining them.
- Violated acceptance: context R4.1 expressly requires rejection of unknown, relative, and nested scripts unless their identity/content and execution semantics are proved; the final spec criterion requires bypass-entry drift to prevent unsealing and maintenance completion.

## Probe method and coverage limits

The probes parsed the reviewed updater as data, loaded only the unchanged `Expand-StartupEnvironment` and `Test-UnprotectedStartupAction` function definitions, replaced `Initialize-UpgradeProcessJob` with a no-op, and supplied `ParsedArguments` directly. This avoids native process/job creation and command-line splitting inside the classifier. Only the decision functions ran; no reviewed sample command, task, Docker operation, database operation, or physical-device operation was executed. The Windows PowerShell process ran this same in-memory decision probe only. Accordingly these probes establish the classifier failures after ordinary argument tokenization; they are not end-to-end Task Scheduler or deployed-service tests.

Static acceptance coverage included the fixed migration edge/digest, role fencing before blocking application stops, durable marker and journal bindings, cross-process failure-cleanup authority, lock checks, Docker process containment and unresolved daemon intents, same-snapshot backup/isolated restore and semantic fingerprints, auxiliary-asset cleanup, forward-only recovery after 0013/new writes, role/restart restoration, guarded application startup, controller Plan/Apply changes, and maintenance bypass checks in desktop/remote entry points. The audit did not comprehensively review the unrelated multi-device product implementation included in the combined diff. No project file was changed and no test suite was run. The findings file is the only audit output written.

The spec explicitly separates local implementation from later release/deployment work. Final release regression, limited commit and signed-candidate reconstruction, real API/GW/Web candidate startup/health checks, actual target launcher installation and task/ACL verification, production Plan/Apply and data/audit checks, and approved field collection remain later gates. Their incompleteness is **not** reported here as an implementation defect. Existing test counts were not independently rerun or treated as proof of target deployment or physical acceptance.

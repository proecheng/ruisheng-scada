# B-04 网络控制矩阵

本文件定义 B-04 的现状基线、目标流量矩阵、配置校验和验收证据。具体 CIDR、地址、端口、证书和责任人只能取自已批准的 `site-acceptance-profile.md`，不得由实施人员临场补写。

## 已验证现状

| 对象 | 当前行为 | B-04 风险 |
|---|---|---|
| Web | Compose 发布 `80:80`；Nginx 监听 80 并代理全部 `/api/` 和 `/ws` | 无 TLS 配置；API 管理路径与用户路径共享入口且没有路由 ACL |
| API | Compose 未发布 API 端口；`/api/health/live`、`ready`、`metrics` 需要补独立管理凭据 | 虽无直接宿主机端口，但健康/指标随全部 `/api/` 被 Web 代理，且 Docker hairpin 可伪装为允许网关 |
| WebSocket | 浏览器以 `/ws?token=<access_jwt>` 建连 | 若代理记录完整请求目标，访问令牌会进入访问日志 |
| GW 设备面 | Compose 发布 `5020:5020`，服务默认监听 `0.0.0.0` | 所有宿主机接口可能接收设备连接，应用源 IP 检查不能替代网络 ACL |
| GW 管理面 | Compose 发布 `9090:9090`，三个端点需要来源 ACL 与独立管理凭据 | health、ready 和 metrics 可能因 Docker hairpin NAT 绕过单一来源 ACL |
| PostgreSQL / Redis | Compose 未发布宿主机端口 | 必须保持内部可达且外部不可达，防止 override 或 host network 回退 |

## 目标流量矩阵

`允许` 表示仍须满足 Profile 中的源地址、目标地址、端口和传输控制；未列出的流量默认拒绝。

| 来源区域 | 目标/路径 | 结论 | 必需控制 | 最小证据 |
|---|---|---|---|---|
| 批准用户网段 | Web 静态页面、业务 `/api/`、`/ws` | 允许 | 仅从批准入口进入；共享/不受信链路使用 HTTPS/WSS；业务鉴权保持 | 页面、登录、受保护 API 和 WebSocket 正向测试 |
| 批准用户网段 | API `/api/health/live`、`ready`、`metrics` | 拒绝 | Nginx 路由 ACL、独立管理入口或等效控制 | 三条路径均得到拒绝或网络不可达 |
| 批准用户网段 | `gw:5020`、`gw:9090`、PostgreSQL、Redis、API 容器端口 | 拒绝 | 网络分区、绑定和防火墙 | TCP 探测均失败 |
| 批准设备网段 | `gw:5020` | 允许 | 源 CIDR allowlist；只绑定批准设备接口或有等效主机 ACL | 已批准设备/测试源连接成功，非登记源按设备契约拒绝 |
| 批准设备网段 | Web、`gw:9090`、PostgreSQL、Redis、API 容器端口 | 拒绝 | 网络分区、绑定和防火墙 | TCP/HTTP 探测均失败 |
| 批准运维/监控网段 | API live/ready/metrics 的受控管理路径 | 允许 | 源 ACL 与独立 Bearer 管理凭据同时通过；不经普通用户入口暴露 | 三条 API 路径正向测试及身份/源证据 |
| 批准运维/监控网段 | GW `/health`、`/ready`、`/metrics` | 允许 | 仅通过管理地址/端口，且源 ACL 与独立 Bearer 管理凭据同时通过 | 三条 GW 路径正向测试 |
| 批准运维/监控网段 | `gw:5020` | 拒绝，除非该源也被明确批准为设备源 | 默认拒绝，职责网段不自动继承 | TCP 探测失败或双角色批准记录 |
| 未批准网段 | Web、业务 API、WebSocket、`gw:5020`、所有管理端点 | 拒绝 | 上游 ACL、宿主机防火墙和绑定共同落实 | DNS 与直接地址、全部目标端口的反向测试 |
| 任意宿主机外部来源 | API、PostgreSQL、Redis 容器端口 | 拒绝 | 不发布端口、不使用 host network、不配置未受控代理 | Compose 渲染、监听清单和外部探测 |
| Web 容器 | API 容器端口 | 允许 | 仅内部应用网络 | 容器网络和服务解析证据 |
| API/GW 容器 | PostgreSQL、Redis 容器端口 | 允许 | 仅内部应用网络及最小凭据 | 容器网络和连接就绪证据 |
| API 容器 | 外部通知服务 | 默认拒绝；单独授权后条件允许 | provider 保持关闭；启用时仅批准目标、凭据和时间窗 | Profile 授权、目标 allowlist 和外发审计 |

运维人员需要使用 Web 管理功能时，其来源还必须列入批准用户网段，或在 Profile 中记录双角色；允许管理探针不自动授予业务入口访问权。

## 站点 Profile 输入

开测前必须给出以下确定值，`UNRESOLVED` 不能被脚本默认值替代：

| 类别 | 必填决定 |
|---|---|
| 区域 | 用户、设备、运维/监控、外部服务、未批准测试源的 IPv4/IPv6 CIDR |
| 入口 | Web、`gw:5020`、`gw:9090` 的宿主机绑定地址、发布端口、DNS、NAT/负载均衡关系 |
| TLS | HTTP 仅限隔离网或 HTTPS/WSS；域名、证书链、私钥保管、终止点、续期、吊销/失效处置和 TLS 策略 |
| 管理面 | API/GW 每个 live、ready、metrics 路径的访问主体、来源、认证/ACL 控制、Bearer 令牌 SHA-256 摘要、凭据保管/轮换负责人和监控采集地址；不得记录原始令牌 |
| 执行面 | 防火墙/ACL 平台、配置负责人、复核人、持久化方式、变更和回滚窗口 |
| 探测 | 四类来源的实际执行位置、地址族、工具、时间窗、授权和证据保存位置 |
| 审批 | Profile ID/版本、候选 ID、项目负责人、运维负责人、客户代表及安全/合规负责人决定 |

若 TLS 在候选外部设备终止，Profile 还必须证明终止点到 Web 的链路位于受控网络，并且 Web 的宿主机地址不能从其他来源绕过终止点。若 API、PostgreSQL 或 Redis 实际跨主机，必须暂停 B-04 验收并补充服务间加密、身份认证和密钥轮换设计。

## 候选与 override 契约

- 候选基础 Compose、Nginx 配置、manifest 和 SHA-256 在站点操作前后保持一致。
- 站点 override 只表达已批准差异；它具有版本、校验值、审批记录、访问控制、备份和恢复位置，但不包含在共享验收附件中展开的秘密。
- 最终配置以候选基础文件与站点 override 共同渲染的结果为准。只审查源文件而不审查渲染结果不能通过。
- 渲染校验必须枚举 `ports`、`expose`、`network_mode`、容器网络、绑定地址、代理路由和 TLS 监听；出现未批准端口、host network、API/数据库/Redis 宿主机发布时失败。
- `0.0.0.0`、`::` 或省略 host IP 的发布只在 Profile 明确批准且存在经实测的等效防火墙/上游 ACL 时允许，否则校验失败。
- 若使用 HTTPS/WSS，HTTP 只能关闭或无条件重定向到批准的 HTTPS 域名；HTTP 不得返回登录、刷新、控制或 WebSocket 内容，直接 IP/其他 Host 不得形成旁路。
- 若 Profile 批准仅在隔离可信网使用 HTTP，探测必须证明该入口从共享、不受信和未批准网段均不可达。
- API `/api/health/` 必须从普通用户路由中隔离；不能因为 API 容器没有宿主机端口，就忽略 Nginx 对该前缀的代理。
- API/GW 管理面必须以来源 ACL 和独立 Bearer 管理凭据双重控制；Docker Desktop 把宿主与 hairpin 流量改写成同一网关来源时，认证是不可省略的第二门禁，最终证据必须证明无/错凭据及非运维来源均不可达。
- 容器重建和宿主机重启后重新渲染配置与监听清单，并重复关键正反向探测，证明控制不会随重启丢失。

## 令牌与日志保护

- 反向代理和应用访问日志不得记录 Authorization、Cookie、访问令牌、刷新令牌或包含令牌的完整 WebSocket 查询字符串。
- 若 `/ws?token=` 保留，代理访问日志格式必须排除查询字符串，错误页、调试日志和上游日志也不得回显请求目标；更换握手方式时必须保持 WebSocket 鉴权和吊销语义。
- 使用专用测试令牌执行登录、刷新和 WebSocket 建连后，扫描 Web、API、容器运行时和验收采集日志；发现完整或可复用令牌即 FAIL，测试令牌随后吊销。
- TLS 私钥、管理令牌明文、站点凭据和完整网络设备配置不进入 Git、镜像层、Compose 环境、命令历史、截图或共享证据包；应用只接收管理令牌 SHA-256 摘要，证据只记录摘要指纹、脱敏标识和受控存储引用。

## 探测证据矩阵

每项记录 Profile ID/版本、候选 ID、提交、镜像摘要、源地址/网段、目标 DNS/IP/端口、地址族、命令或操作、开始/结束时间、原始输出位置、执行人和结论。

| 探测位置 | 必须成功 | 必须失败 |
|---|---|---|
| 用户网段 | 批准的 Web、业务 API、WebSocket；适用时 TLS 证书/主机名 | API 管理路径、`gw:5020`、`gw:9090`、API/DB/Redis 直达、HTTP/TLS 旁路 |
| 设备网段 | `gw:5020` 的批准设备流量 | Web、API 管理路径、`gw:9090`、API/DB/Redis 直达 |
| 运维/监控网段 | 批准的 API 与 GW live/ready/metrics | 未批准的设备端口和内部服务；未授予用户角色时业务 Web/API |
| 未批准网段 | 无 | Web/DNS 与直接 IP、业务 API、WebSocket、`gw:5020`、所有管理路径和内部服务 |
| 目标宿主机 | 容器所需内部连接、批准绑定地址 | 未批准宿主机监听、意外 IPv6 监听、host network、重启后规则丢失 |

TLS/WSS 探测还必须覆盖证书链、主机名、有效期、批准 TLS 策略、HTTP 行为、直接 IP/替代 Host 和 WebSocket 升级。端口探测不能只记录超时，还要结合监听清单和防火墙计数器区分拒绝、丢弃与测试路径错误。

## B-04 解锁条件

B-04 仅在以下条件同时满足时由 BLOCKED 改为 PASS：

1. 网络、安全和探测相关 Profile 字段全部获批，没有适用的 `UNRESOLVED`。
2. 候选基础文件完整性保持，站点 override 已版本化、校验、审批并可恢复。
3. 渲染配置、监听清单、容器网络、防火墙/ACL 和 TLS 配置均符合目标流量矩阵。
4. 四类来源的所有适用正向与反向探测通过，IPv4/IPv6 均有执行或显式禁用证据。
5. TLS 无旁路，管理端点不从用户、设备或未批准网段暴露，API/DB/Redis 无宿主机外部入口。
6. 专用测试令牌未出现在任何收集日志或验收附件，真实秘密未进入证据包。
7. 容器和宿主机重启后关键控制与探测结果保持，并由项目负责人、运维负责人和客户代表签署。

任一适用项 FAIL/BLOCKED、任何未关闭 P0/P1、未批准的 N/A 或仅凭配置声明而没有源网段实测，均不得关闭 B-04 或宣布 Plan 5 完成。

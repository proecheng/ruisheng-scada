# DO 逐路控制修复（2026-09-21）

## 根因及协议

9月21日15:34现场只读核对发现：通用控制页发送 FC06 寄存器命令；API 将指令记入 PostgreSQL 和 Redis 后，网关没有控制消费者。现场保留5条9月15日历史 pending 命令，Redis消费者组为空。此前“已下发”提示只代表受理，未形成串口执行闭环。

板端已确认两路DO回读为FC03寄存器1的最低两位，0/1/2/3对应00/01/10/11。用户提供的FC05命令分别使用线圈0、1，高电平FF00、低电平00FF（此板的自定义值）。不把0～3当作写寄存器值，也不假设支持FC0F同时写多个线圈。

## 修复行为

设备启用明确的 `two_channel_fc05_00ff_v1` 控制协议后，远程控制页分别显示DO1、DO2当前回读，每路可选保持不变、高、低。默认均保持不变。确认框绑定当时的通道、目标值和配置版本，配置变化必须重新确认。

API验证租户、控制权限、设备启用状态、协议配置、配置版本和在途命令，保存唯一命令及15秒有效期。网关只相信数据库内审计值，不使用Redis消息携带的寄存器或目标值。执行前持久记录dispatched_at；重启、重复消息、旧命令、超时或已取消命令都不重放输出。

串口使用既有单一轮询任务执行控制：先读取当前两路状态，再依次FC05写所选通道，每次核对CRC、地址、完整回显及FC03回读，并校验另一位未改变。多路不是原子同时改变；某一路失败立即停止，保留已确认通道和未确认部分。写操作不自动重试，不自动回滚物理输出。控制间穿插正常采样，单寄存器验证不会作为不完整采样写入历史。

回归测试还复现了Python3.11中wait_for与采样完成同轮发生时可能吞掉取消的竞争，改为同任务的asyncio.timeout，使串口停机取消正常传递。

## 用法和现场待验

强制刷新后进入DEV001“远程控制”，每路选择高电平、低电平或保持不变，再点击“应用所选电平”，输入DEV001确认。bit0对应DO1，bit1对应DO2；0为两低，1为DO1高/DO2低，2为DO1低/DO2高，3为两高。这些是回读编码，不能据此用FC06写读回寄存器。

用户已确认当前无负载。先记录原始电平，逐路切换、检查另一位保持，最后恢复原始状态。发生超时应停下并保存时间和结果，不能连点重试；板端可能已经动作。完整步骤见 `field-test-steps.md`。现场实际DO电平、板断电/USB拔插/DI变化均尚未收到操作时间与结果，不计为通过。浏览器控制工具当前无法取得会话授权，实际输出测试由现场通过已有登录界面完成。
